# Decorator Pattern

## Overview

The **Decorator Pattern** is a structural design pattern that allows us to **add new behavior or responsibilities to an object dynamically without modifying its original class**.

Instead of creating many subclasses for every possible combination of features, we wrap the original object with decorator objects.

The basic idea is:

```text
Original Object
      ↓
  Decorator
      ↓
  Decorator
      ↓
Final Object
```

Each decorator adds some additional behavior.

---

# 1. Problem

Suppose we have a coffee shop.

We have a basic coffee:

```text
Coffee
```

Customers can add different extras:

```text
Milk
Sugar
Whipped Cream
Chocolate
```

We could create separate classes for every possible combination:

```text
Coffee
CoffeeWithMilk
CoffeeWithSugar
CoffeeWithMilkAndSugar
CoffeeWithMilkSugarAndChocolate
CoffeeWithMilkSugarChocolateAndCream
...
```

This quickly becomes a **class explosion**.

For `n` optional features, the number of possible combinations can grow very quickly.

---

# 2. Problem With Inheritance

One possible solution is inheritance:

```text
Coffee
  ↑
  ├── CoffeeWithMilk
  ├── CoffeeWithSugar
  ├── CoffeeWithChocolate
  └── CoffeeWithMilkAndSugar
```

But this approach has problems.

### Class Explosion

Every new combination may require a new class.

For example:

```text
Coffee
Coffee + Milk
Coffee + Sugar
Coffee + Chocolate
Coffee + Milk + Sugar
Coffee + Milk + Chocolate
Coffee + Sugar + Chocolate
Coffee + Milk + Sugar + Chocolate
...
```

The number of classes becomes difficult to maintain.

### Inflexibility

Inheritance defines behavior at compile time.

But we may want to add features dynamically at runtime.

---

# 3. Solution

The Decorator Pattern uses **composition instead of creating subclasses for every combination**.

Instead of:

```text
CoffeeWithMilk
CoffeeWithSugar
CoffeeWithMilkAndSugar
```

we create decorators:

```text
Coffee
  ↓
MilkDecorator
  ↓
SugarDecorator
```

Each decorator wraps another `Coffee`.

---

# 4. Basic Structure

The Decorator Pattern has four main components:

```text
Component
   ↑
   ├── ConcreteComponent
   │
   └── Decorator
          ↑
          ├── ConcreteDecoratorA
          └── ConcreteDecoratorB
```

### Components

- **Component** → common interface
- **Concrete Component** → original object
- **Decorator** → base decorator
- **Concrete Decorators** → add additional behavior

---

# 5. Component

Let's create a common interface for coffee.

```java
public interface Coffee {

    double cost();

    String description();
}
```

The `Coffee` interface defines the operations that both the original object and decorators must support.

```text
Coffee
  │
  ├── cost()
  └── description()
```

---

# 6. Concrete Component

Now we create the basic coffee.

```java
public class SimpleCoffee implements Coffee {

    @Override
    public double cost() {
        return 50;
    }

    @Override
    public String description() {
        return "Simple Coffee";
    }
}
```

This is the original object that will be decorated.

---

# 7. Decorator

The Decorator also implements the same `Coffee` interface.

It contains another `Coffee` object.

```java
public abstract class CoffeeDecorator implements Coffee {

    protected Coffee coffee;

    public CoffeeDecorator(Coffee coffee) {
        this.coffee = coffee;
    }

    @Override
    public double cost() {
        return coffee.cost();
    }

    @Override
    public String description() {
        return coffee.description();
    }
}
```

The important part is:

```java
protected Coffee coffee;
```

The decorator **wraps** another `Coffee`.

This is the key concept of the Decorator Pattern.

---

# 8. Concrete Decorator - Milk

Now we create a decorator that adds milk.

```java
public class MilkDecorator extends CoffeeDecorator {

    public MilkDecorator(Coffee coffee) {
        super(coffee);
    }

    @Override
    public double cost() {
        return coffee.cost() + 10;
    }

    @Override
    public String description() {
        return coffee.description() + ", Milk";
    }
}
```

The decorator:

1. Delegates the existing behavior to the wrapped object.
2. Adds its own behavior.

For example:

```java
coffee.cost() + 10
```

---

# 9. Concrete Decorator - Sugar

We can create another decorator:

```java
public class SugarDecorator extends CoffeeDecorator {

    public SugarDecorator(Coffee coffee) {
        super(coffee);
    }

    @Override
    public double cost() {
        return coffee.cost() + 5;
    }

    @Override
    public String description() {
        return coffee.description() + ", Sugar";
    }
}
```

Now sugar can be added independently of milk.

---

# 10. Concrete Decorator - Chocolate

Another decorator:

```java
public class ChocolateDecorator extends CoffeeDecorator {

    public ChocolateDecorator(Coffee coffee) {
        super(coffee);
    }

    @Override
    public double cost() {
        return coffee.cost() + 20;
    }

    @Override
    public String description() {
        return coffee.description() + ", Chocolate";
    }
}
```

---

# 11. Using Decorators

We can start with:

```java
Coffee coffee = new SimpleCoffee();
```

At this point:

```text
SimpleCoffee
```

Cost:

```text
50
```

Now add milk:

```java
coffee = new MilkDecorator(coffee);
```

Structure:

```text
MilkDecorator
      ↓
SimpleCoffee
```

Cost:

```text
50 + 10 = 60
```

Now add sugar:

```java
coffee = new SugarDecorator(coffee);
```

Structure:

```text
SugarDecorator
      ↓
MilkDecorator
      ↓
SimpleCoffee
```

Cost:

```text
50 + 10 + 5 = 65
```

Now add chocolate:

```java
coffee = new ChocolateDecorator(coffee);
```

Final structure:

```text
ChocolateDecorator
        ↓
  SugarDecorator
        ↓
   MilkDecorator
        ↓
   SimpleCoffee
```

Final cost:

```text
50 + 10 + 5 + 20 = 85
```

---

# 12. Complete Client

```java
public class Client {

    public static void main(String[] args) {

        Coffee coffee =
                new SimpleCoffee();

        coffee =
                new MilkDecorator(coffee);

        coffee =
                new SugarDecorator(coffee);

        coffee =
                new ChocolateDecorator(coffee);

        System.out.println(coffee.description());
        System.out.println(coffee.cost());
    }
}
```

Output:

```text
Simple Coffee, Milk, Sugar, Chocolate
85.0
```

---

# 13. Execution Flow

The final object looks like:

```text
                    ChocolateDecorator
                            │
                            ↓
                      SugarDecorator
                            │
                            ↓
                       MilkDecorator
                            │
                            ↓
                       SimpleCoffee
```

When we call:

```java
coffee.cost();
```

the call moves through the decorators.

```text
ChocolateDecorator.cost()
        ↓
SugarDecorator.cost()
        ↓
MilkDecorator.cost()
        ↓
SimpleCoffee.cost()
```

Then the values are added while returning:

```text
SimpleCoffee
    50
     ↓
MilkDecorator
    50 + 10 = 60
     ↓
SugarDecorator
    60 + 5 = 65
     ↓
ChocolateDecorator
    65 + 20 = 85
```

---

# 14. Why Does Decorator Implement the Same Interface?

This is one of the most important concepts.

Both:

```text
SimpleCoffee
```

and:

```text
MilkDecorator
```

implement:

```text
Coffee
```

Therefore:

```java
Coffee coffee = new SimpleCoffee();
```

and:

```java
Coffee coffee = new MilkDecorator(coffee);
```

are both valid.

This allows decorators to be stacked.

```text
Coffee
  ↑
  ├── SimpleCoffee
  │
  └── CoffeeDecorator
          ↑
          ├── MilkDecorator
          ├── SugarDecorator
          └── ChocolateDecorator
```

---

# 15. Composition Over Inheritance

The Decorator Pattern is a classic example of:

> **Favor composition over inheritance.**

Instead of creating:

```text
CoffeeWithMilk
CoffeeWithSugar
CoffeeWithMilkAndSugar
```

we compose objects:

```text
SugarDecorator
      ↓
MilkDecorator
      ↓
SimpleCoffee
```

The behavior is built dynamically by wrapping objects.

---

# 16. Decorator vs Inheritance

### Inheritance

```text
Coffee
  ↑
  ├── CoffeeWithMilk
  ├── CoffeeWithSugar
  └── CoffeeWithMilkAndSugar
```

Problems:

- More classes
- Fixed behavior
- Class explosion
- Difficult combinations

### Decorator

```text
SugarDecorator
      ↓
MilkDecorator
      ↓
SimpleCoffee
```

Advantages:

- Dynamic behavior
- Flexible combinations
- No class explosion
- Multiple decorators can be stacked

---

# 17. Runtime Behavior

One of the biggest benefits of the Decorator Pattern is that behavior can be added at runtime.

For example:

```java
Coffee coffee =
        new SimpleCoffee();
```

Then:

```java
coffee =
        new MilkDecorator(coffee);
```

Then:

```java
coffee =
        new SugarDecorator(coffee);
```

Then:

```java
coffee =
        new ChocolateDecorator(coffee);
```

The object's behavior changes dynamically.

---

# 18. Order of Decorators Matters

Decorators can be applied in different orders.

For example:

```java
coffee =
        new MilkDecorator(
                new SugarDecorator(
                        new SimpleCoffee()
                )
        );
```

versus:

```java
coffee =
        new SugarDecorator(
                new MilkDecorator(
                        new SimpleCoffee()
                )
        );
```

The structure is different.

In our simple cost example, the final price is the same because addition is commutative.

But in real applications, decorator order can matter.

For example:

```text
Compression
    ↓
Encryption
    ↓
Data
```

is not necessarily equivalent to:

```text
Encryption
    ↓
Compression
    ↓
Data
```

---

# 19. Real-World Example

The Java I/O API is a famous example of the Decorator Pattern.

For example:

```java
InputStream input =
        new BufferedInputStream(
                new FileInputStream("file.txt")
        );
```

Here:

```text
FileInputStream
      ↓
BufferedInputStream
```

`BufferedInputStream` adds buffering behavior around the existing `InputStream`.

Another example:

```java
InputStream input =
        new DataInputStream(
                new BufferedInputStream(
                        new FileInputStream("file.txt")
                )
        );
```

Now multiple behaviors are combined:

```text
DataInputStream
       ↓
BufferedInputStream
       ↓
FileInputStream
```

---

# 20. Decorator Structure

General structure:

```text
                    Component
                       ↑
             ┌─────────┴─────────┐
             │                   │
             │                   │
     ConcreteComponent       Decorator
                                 ↑
                         ┌───────┴───────┐
                         │               │
                  ConcreteDecoratorA  ConcreteDecoratorB
```

Decorator contains:

```text
Component
   ↑
Decorator
   │
   └── wraps Component
```

---

# 21. Important Concept: Same Type

The decorator and the object being decorated have the same abstraction.

```text
Component
   ↑
   ├── ConcreteComponent
   │
   └── Decorator
          │
          └── Component
```

This means:

```java
new MilkDecorator(coffee)
```

is possible because:

```text
MilkDecorator → Coffee
```

and the constructor accepts:

```java
Coffee
```

---

# 22. Advantages

## 1. Adds Behavior Dynamically

Behavior can be added at runtime.

```java
coffee =
        new MilkDecorator(coffee);
```

---

## 2. Avoids Class Explosion

We don't need a separate class for every combination.

---

## 3. Flexible

Decorators can be combined in different ways.

```text
Milk
Sugar
Chocolate
```

can be independently added.

---

## 4. Follows Open/Closed Principle

We can introduce new decorators without modifying the existing component.

For example:

```java
class CaramelDecorator extends CoffeeDecorator {
    ...
}
```

The existing `SimpleCoffee` does not need to change.

---

## 5. Single Responsibility

Each decorator can focus on one additional behavior.

```text
MilkDecorator
    → Adds milk

SugarDecorator
    → Adds sugar

ChocolateDecorator
    → Adds chocolate
```

---

# 23. Disadvantages

## 1. Many Small Objects

Using many decorators can create many objects.

```text
Decorator
   ↓
Decorator
   ↓
Decorator
   ↓
Decorator
```

This can make debugging more difficult.

---

## 2. Complex Object Structure

A deeply nested decorator chain can be difficult to understand.

```text
A
 ↓
B
 ↓
C
 ↓
D
 ↓
E
```

---

## 3. Debugging Can Be Difficult

A method call may pass through several decorators before reaching the original object.

---

## 4. Order Can Matter

Different decorator orders can produce different behavior.

---

# 24. Decorator vs Adapter

These patterns are sometimes confused.

### Decorator

Purpose:

> Add behavior without changing the interface.

```text
Component
    ↑
Decorator
```

The decorator keeps the same interface.

---

### Adapter

Purpose:

> Convert one interface into another interface.

```text
Client
  ↓
Adapter
  ↓
Existing Class
```

The Adapter changes the interface expected by the client.

---

# 25. Decorator vs Proxy

Decorator and Proxy have similar structures because both wrap another object.

But their intent is different.

### Decorator

Adds responsibilities or behavior.

```text
Object
  ↓
Decorator
  ↓
Enhanced Object
```

### Proxy

Controls access to an object.

```text
Client
  ↓
Proxy
  ↓
Real Object
```

Examples of Proxy behavior:

- Lazy loading
- Access control
- Caching
- Remote access

---

# 26. Key Takeaways

1. **Decorator Pattern** is a structural design pattern.

2. It adds behavior or responsibilities to an object dynamically.

3. It avoids creating subclasses for every combination of features.

4. Decorators implement the same interface as the object they decorate.

5. A decorator contains a reference to the component it wraps.

6. Multiple decorators can be chained.

7. Decorator is based heavily on **composition**.

8. It is a classic example of:

```text
Favor Composition Over Inheritance
```

9. Behavior can be added at runtime.

10. The order of decorators can matter.

11. Java I/O streams are a common real-world example.

---

# 27. Final Summary

The main idea of the Decorator Pattern is:

> **Wrap an object with another object that implements the same interface and adds additional behavior.**

Instead of:

```text
Coffee
  ↓
CoffeeWithMilk
  ↓
CoffeeWithMilkAndSugar
  ↓
CoffeeWithMilkSugarAndChocolate
```

we use:

```text
ChocolateDecorator
        ↓
  SugarDecorator
        ↓
   MilkDecorator
        ↓
   SimpleCoffee
```

Each decorator adds one responsibility.

The overall structure is:

```text
                  Component
                     ↑
          ┌──────────┴──────────┐
          │                     │
 ConcreteComponent          Decorator
                                │
                         ┌──────┴──────┐
                         ↓             ↓
                   Decorator A   Decorator B
```

The key relationship is:

```text
Decorator
    │
    └── has-a → Component
```

Therefore:

> **Decorator uses composition to dynamically add behavior while keeping the same interface.**
